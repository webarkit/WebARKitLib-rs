## Implications for M6-2

### Dual-mode validation strategy

Following the M6-1 precedent (`fastsqrt1` is dead code → no dual-mode test), the M6-2 dual-mode FFI bridges should target only the **3 live solver entrypoints**:

- ✅ `webarkit_cpp_solve_null_vector_8x9_destructive`
- ✅ `webarkit_cpp_solve_symmetric_linear_system_3x3`
- ✅ `webarkit_cpp_solve_linear_system_2x2`

Each gets a parametric Rust-vs-C++ comparison test behind `#[cfg(feature = "dual-mode")]`.

The dead-code functions still get ported (for completeness, mirroring M6-1's treatment of `fastsqrt1`/`fastatan2`/`fastatan2_360`) but only get unit tests against analytic solutions — no FFI bridge.

### Doc-comment guidance for ported functions

Per the M6-1 pattern, every function should carry an upstream-status note in its doc comment:

- For the 3 live entrypoints: cite the call site (e.g. `harris.cpp:633`).
- For transitively-live helpers: explain which entrypoint reaches them.
- For dead-code functions: explicitly note "defined in `<header>:<line>` but never called from anywhere in the upstream FreakMatcher (verified at submodule rev 656436e36b)" — exactly the wording used for `fastsqrt1` in M6-1.

### Function porting priority

If we ever need to defer functions to a later milestone, this is the priority order:

1. **Must-have** (live entrypoints + their reachable closures): `SolveNullVector8x9Destructive` + the 8 `OrthogonalizePivot8x9Basis*` + `OrthogonalizeIdentity8x9` + `AccumulateProjection9` + `DotProduct9` + `SumSquares9` + `ScaleVector9` + `AccumulateScaledVector9`; `SolveSymmetricLinearSystem3x3` + `MatrixInverseSymmetric3x3` + `DeterminantSymmetric3x3` + `Cofactor2x2` variants + `Multiply_3x3_3x1`; `SolveLinearSystem2x2` + `MatrixInverse2x2` + `Determinant2x2` + `Multiply_2x2_2x1`.
2. **Nice-to-have** (called outside the homography path, but still production): `DotProduct4`, `AddScaledVectors4`, `ScaleVector{4,8}`.
3. **Defer-able** (dead code, but on the spec deliverable list): `SolveTridiagonalDestructive`, `UpdateOuterProduct2x2`, `UpdateGaussNewtonOperations2x2`. Recommend porting them anyway for completeness, with the dead-code doc note.

### Cauchy functions removed from scope

Per chat clarification (Italian, archived in this session): `cauchy_cost` and `cauchy_cost_jac` were listed in #64 by mistake. They actually belong to `math/robustifiers.h` and `homography_estimation/robust_homography.h`, which are M6-3 territory. The corrected M6-2 scope omits both.

## Cross-Reference: M6-1 Precedent

The same audit methodology in M6-1 found that `fastsqrt1`, `fastatan2`, and `fastatan2_360` were all dead code in upstream — only `fastexp6` had a live caller (`orientation_assignment.cpp:186`). That finding shaped the M6-1 dual-mode strategy (only `fastexp6` got an FFI bridge that produced bit-identical results; the others got loose-tolerance tests that surfaced an upstream `(int)x` truncation bug in `fastsqrt1`).

The M6-2 audit applies the same lens and produces a comparable finding: most spec deliverables are transitively live via 3 production entrypoints, and 3 are outright dead code.
